Understand DAX first · Concept 1
What is DAX?
DAX stands for Data Analysis Expressions. It's the formula language of Power BI — you use it to create calculations that your visuals and KPI cards pull from. Think of it as Excel formulas, but built for tables with relationships instead of individual cells.
1
DAX vs Excel vs M — what's the difference?
▼
LanguageWhere it runsWhat it doesYou used it in
MPower Query EditorCleans and shapes raw data before it loadsPhase 1
DAXReport / Model viewCalculates values from already-loaded, clean dataPhase 3 ← you are here
Excel formulasExcel cellsWorks on individual cells in a gridNot in Power BI
💡 The key difference from Excel: DAX doesn't work on individual cells. It works on entire columns and tables at once, and it respects the relationships you set up in Phase 2. When you write a DAX measure, it automatically adjusts based on whatever filter is applied in the visual — more on that when we cover filter context.
2
What DAX will do for your dashboard
▼

Every number your dashboard displays will come from a DAX measure. Here's what you'll build in this phase:

CategoryWhat it answers
Funnel KPIsHow many applicants reached each stage? What % got hired?
SalaryWhat's the median monthly salary for each role?
SkillsWhich skills appear in the most job postings?
FairnessIs the hire rate different across gender, education, or age group?
Time intelligenceHow many applications were submitted per month?
Understand DAX first · Concept 2
Measures vs calculated columns
DAX can create two things: measures and calculated columns. Beginners often mix these up. Understanding the difference will save you a lot of confusion.
1
The core difference
▼
MeasureCalculated column
What it isA formula that calculates at query timeA new column added to a table
When it calculatesEvery time a visual renders or a filter changesOnce when data loads, stored in the table
What it returnsA single value (a number, a %)A value for every row
Responds to slicers?✅ Yes — automatically❌ No — it's fixed per row
ExampleHire Rate = 6.1%age_band = "25–34"
⚠️ Almost everything you build in Phase 3 will be measures — not calculated columns. You already created calculated columns in Phase 1 (age_band, salary_midpoint). Measures are for KPIs and aggregations that need to respond to filters.
2
A simple test to know which one to use
▼

Ask: "Do I want a different value per row, or a single summary value across many rows?"

Different value per row (one result per application, one result per job) → Calculated column

A single summary that changes based on filters (total hired, average score, hire rate) → Measure

💡 If you're ever unsure — default to a measure. Measures are more flexible, use less memory, and respond to your dashboard's slicers automatically. Calculated columns are rigid and take up storage.
Understand DAX first · Concept 3
How to write a measure in Power BI
Before writing any specific measures, here's the mechanics — where to type it, what the syntax looks like, and how to read a DAX formula without getting lost.
1
Where to create a measure
Report view or Model view
▼
▶ Home tab → New Measure —or— right-click a table → New Measure
  1. In Report view or Model view, go to the Home tab → click New Measure. A formula bar appears at the top.
  2. Alternatively: in the Fields panel on the right, right-click any table name → New Measure. This also controls which table the measure lives in.
  3. Type your formula in the bar and press Enter or click the checkmark ✓ to save. Press Esc to cancel without saving.
💡 Best practice: create a blank table called _Measures to store all your measures in one place. This keeps the Fields panel tidy. We'll set this up in the last step of this guide.
2
Anatomy of a DAX formula
▼

Every measure follows this structure. Let's break down a real one:

Total Applications = COUNTROWS( fact_applications )
Total Applications
The measure name — this is what appears in the Fields panel and in your visuals. Make it readable, like a label.
=
Every measure starts with an equals sign — just like Excel.
COUNTROWS
A DAX function — this one counts the number of rows in a table. Functions are always in CAPS.
fact_applications
The table name — always written in plain text, no brackets. This tells DAX which table to look at.
💡 Column references look like table[column] — for example fact_applications[status]. The table name comes first, then the column in square brackets. You'll see this pattern in every measure.
3

▼

Understand DAX first · Concept 4
What is filter context?
Filter context is the most important concept in DAX. Once this clicks, everything else makes sense. It's the reason why the same measure shows a different number depending on where it's placed in a visual.
1
The analogy — a moving spotlight
▼

Imagine your entire fact_applications table is a stage with 2,659 actors (rows). A DAX measure is a person counting how many actors are on stage. Filter context is the spotlight — it determines which part of the stage is visible when the counting happens.

When you put Total Applications in a bar chart with work_setup on the axis, Power BI automatically shines the spotlight on just the "Remote" rows, counts them, then moves to "Hybrid", counts again, then "Onsite". The measure itself never changes — the filter context does.

💡 This is why a single measure like Total Applications = COUNTROWS(fact_applications) can show 2,659 on a KPI card (no filter), 890 in the "Remote" bar (filtered by work_setup), and 45 in a specific month's column (filtered by date). Same measure, different filter context, different result.
2
What creates filter context
▼

Four things automatically create filter context in your dashboard:

SourceExample
A slicer on the pageUser selects "Hybrid" in a work_setup slicer → all measures on the page now only see Hybrid rows
A visual's axis or legendBar chart with job_title on axis → each bar has its own filter context
A visual's filters paneYou pin a filter on the visual for status = "Hired"
CALCULATE inside a measureYou explicitly override the filter context inside a formula
⚠️ The first three happen automatically — you don't write any DAX for them. The fourth (CALCULATE) is how you write measures that ignore or override the current filter context, which is how things like "% of total" work.
Funnel KPIs · Measure 1
Total Applications
Your first and simplest measure — count all rows in fact_applications. This becomes the denominator for almost every other measure you'll write, so it's the right place to start.
1
Write the measure
▼
▶ Home → New Measure
Total Applications = COUNTROWS( fact_applications )
COUNTROWS
Counts every visible row in the table — "visible" meaning whatever passes the current filter context.
fact_applications
The table to count rows from. No column needed — COUNTROWS counts entire rows.
Expected result

On a KPI card with no filters: 2,659. In a bar chart filtered by work_setup: different number per bar. On a table filtered by "Hired": 163.

Funnel KPIs · Measures 2–7
Count by funnel stage
Your hiring funnel has 6 stages: Applied → Screened → Interviewed → Offered → Hired → Rejected. You need a count measure for each stage. This is where CALCULATE comes in for the first time.
1
What CALCULATE does
▼

CALCULATE is the most important function in DAX. It takes an existing measure or expression and evaluates it under a modified filter context that you specify.

CALCULATE( expression, filter1, filter2, ... )

In plain English: "calculate this expression, but only for rows where these filter conditions are true."

💡 Think of CALCULATE like a WHERE clause in SQL. CALCULATE(COUNTROWS(fact_applications), fact_applications[status] = "Hired") is the same as SELECT COUNT(*) FROM fact_applications WHERE status = 'Hired'.
2
Write all 6 stage count measures
▼

Create a new measure for each one. Notice they all follow the exact same pattern — only the status value changes:

Applied = CALCULATE( COUNTROWS(fact_applications), fact_applications[status] = "Applied" ) Screened = CALCULATE( COUNTROWS(fact_applications), fact_applications[status] = "Screened" ) Interviewed = CALCULATE( COUNTROWS(fact_applications), fact_applications[status] = "Interviewed" ) Offered = CALCULATE( COUNTROWS(fact_applications), fact_applications[status] = "Offered" ) Hired = CALCULATE( COUNTROWS(fact_applications), fact_applications[status] = "Hired" ) Rejected = CALCULATE( COUNTROWS(fact_applications), fact_applications[status] = "Rejected" )
Expected values (no filters applied)
MeasureExpected result
Applied365
Screened800
Interviewed457
Offered100
Hired163
Rejected774
⚠️ These numbers represent the furthest stage reached — "Screened" means they were screened but not interviewed. This is how your raw data was designed. The funnel visual in Phase 4 will show the cumulative drop-off.
Funnel KPIs · Measures 8–9
Hire rate & offer rate
Rates are where DAX starts to feel powerful — one small formula gives you a percentage that automatically adjusts to any slicer on the page.
1
Why DIVIDE instead of just dividing with /
▼

In DAX you could write [Hired] / [Total Applications], but if Total Applications is ever zero (for example, a filter returns no rows), this throws a division-by-zero error and breaks your visual.

DIVIDE handles this gracefully — it returns a blank (or a value you specify) instead of an error whenever the denominator is zero.

DIVIDE( numerator, denominator, alternate_result ) // alternate_result is optional — defaults to blank if omitted
2
Write hire rate and offer rate
▼
Hire Rate = DIVIDE( [Hired], [Total Applications] ) Offer Rate = DIVIDE( [Offered], [Total Applications] )
💡 Notice the formula references [Hired] and [Total Applications] in square brackets — these are the measures you already created, not table columns. Measures referencing other measures is called measure chaining and is a core DAX pattern. Change [Hired] once, and Hire Rate updates automatically.
Format these as percentages
  1. Click the Hire Rate measure in the Fields panel to select it.
  2. In the Measure tools tab that appears, click the % button and set decimal places to 1.
  3. Repeat for Offer Rate.

Expected: Hire Rate ≈ 6.1%, Offer Rate ≈ 3.8%

Salary · Measures 13–15
Median & average salary
Salary measures work on dim_jobs, not fact_applications — because salary info lives in the job posting, not per application. These are the simplest measures you'll write.
1
Write median and average salary measures
▼
Median Salary = MEDIAN( dim_jobs[salary_midpoint] ) Avg Salary = AVERAGE( dim_jobs[salary_midpoint] ) Salary Range Min = AVERAGE( dim_jobs[salary_min] ) Salary Range Max = AVERAGE( dim_jobs[salary_max] )
💡 Why MEDIAN over AVERAGE for salary? Salary distributions are almost always skewed — a few very high salaries pull the average up and make it unrepresentative. The median (middle value) is a more honest picture of what a typical job pays. Use both on your dashboard so viewers can see the difference.
⚠️ These use salary_midpoint — the column you created in Phase 1 by averaging salary_min and salary_max per job. Rows where salary was "Negotiable" or blank will have null midpoints and are automatically excluded from MEDIAN and AVERAGE calculations.
Salary · Measure 16
Salary by role & work setup
Good news — you don't need to write a separate measure for "median salary for Data Analysts" or "median salary for Remote jobs." The measures you already wrote handle this automatically through filter context.
1
How filter context handles this for you
▼

When you put Median Salary in a bar chart with dim_jobs[job_title] on the axis, Power BI automatically filters dim_jobs to each job title row-by-row and recalculates the median for each one. You don't write a new measure — the same measure works for every breakdown.

💡 This is the payoff from Phase 2. Because dim_jobs has clean, standardised job_title and work_setup columns, you can now slice Median Salary by any of those dimensions without writing extra DAX. The star schema does the heavy lifting.
2
Average interview score — one bonus measure
▼
Avg Interview Score = AVERAGE( fact_applications[interview_score] )

This will automatically respond to slicers — average score for Hired applicants, average score by gender, average score by role. Same pattern, no extra work.

Skills · Measure 17
Job count by skill
This measure tells you how many job postings require each skill — the basis of your "most in-demand skills" bar chart. It works through the bridge table you built in Phase 2.
1
Write the job count by skill measure
▼
Jobs Requiring Skill = COUNTROWS( bridge_job_skills )

That's it — just one line. When you put this in a bar chart with dim_skills[skill_name] on the axis, the bridge table's relationship filters automatically to each skill, and COUNTROWS counts how many rows (job-skill pairs) exist for that skill.

How to build the top skills chart
  1. Add a Bar Chart visual to your report.
  2. Y-axis: dim_skills[skill_name]
  3. X-axis: [Jobs Requiring Skill]
  4. In the visual's filter pane, set Top N filter → Top 10 by Jobs Requiring Skill.
💡 This works because of the many-to-many bridge setup from Phase 2. SQL appearing in 45 jobs shows as 45 on the bar — each row in bridge_job_skills is one job-skill pair, so counting rows = counting jobs that require that skill.
Fairness · Measures 18–19
Hire rate by gender
The fairness page of your dashboard checks whether hiring outcomes differ across demographic groups. The hire rate measure you already wrote handles most of this — but you need one additional measure to show % of total applications per gender.
1
Hire rate by gender — no new measure needed
▼

Your existing [Hire Rate] measure already works for gender breakdown. Put it in a bar chart with fact_applications[gender] on the axis — filter context does the rest.

💡 The data dictionary notes that outcomes were generated independent of demographics, so you should expect near-parity across gender groups. If you see a big gap, it's worth investigating — but with synthetic data it's likely just random variation in small groups like Non-binary and Prefer not to say.
2
% of applications — introducing ALL()
▼

This measure shows what share of all applications each gender represents — e.g. "Female applicants made up 31% of total applications." The trick is ALL(), which removes the current filter so the denominator is always the grand total.

% of Applications = DIVIDE( [Total Applications], CALCULATE( [Total Applications], ALL( fact_applications[gender] ) ) )
ALL( fact_applications[gender] )
Removes any filter on the gender column — so the denominator counts all 2,659 applications regardless of which gender is in context.
⚠️ This measure is gender-specific — if you reuse it in a chart sliced by education or age_band instead, the ALL() on gender column won't help. For a fully general "% of total" measure you'd use ALL(fact_applications) instead — but that removes all filters, which may not always be what you want.
Fairness · Measure 20
Hire rate by education & age band
No new measures needed here either. Your existing Hire Rate and Total Applications measures work automatically when you drop education or age_band onto a visual's axis.
1
Average years of experience by status
▼

One extra measure that adds insight to the fairness page — does experience level affect hiring outcomes?

Avg Years Experience = AVERAGE( fact_applications[years_experience] )

Put this in a table visual alongside status to see whether Hired applicants had more experience on average than Rejected ones. Filter context handles the breakdown automatically.

Time Intelligence · Measure 21
Postings over time
Time intelligence measures let you slice your data by month, quarter, or year using the dim_date table you created in Phase 2. This is where marking dim_date as a Date Table pays off.
1
Total job postings measure
▼
Total Job Postings = COUNTROWS( dim_jobs )

Put this in a line chart with dim_date[MonthName] on the axis to see postings per month. Because dim_date is connected to dim_jobs[posted_date], the date filter automatically flows into the job count.

💡 Use dim_date[YearMonth] (format: "2026-01") on the axis instead of MonthName if you want the months to sort chronologically. Month names sort alphabetically by default (April before January) unless you set a sort-by column.
2
Cumulative postings (running total)
▼
Cumulative Postings = CALCULATE( [Total Job Postings], FILTER( ALL( dim_date ), dim_date[Date] <= MAX( dim_date[Date] ) ) )
ALL( dim_date )
Removes the current date filter so we can look back at all prior dates.
Date <= MAX(Date)
Re-applies a new filter: only dates up to and including the current date in context. This creates the running total effect.
Time Intelligence · Measures 22–23
Applications month-to-date & by month
Two more time measures that make your dashboard feel professional — a month-to-date running total and a clean monthly breakdown of applications.
1
Applications by month and MTD
▼
Applications by Month = CALCULATE( [Total Applications], ALLEXCEPT( dim_date, dim_date[YearMonth] ) ) Applications MTD = TOTALMTD( [Total Applications], dim_date[Date] )
💡 TOTALMTD is a built-in time intelligence shortcut — it calculates a running total from the start of the current month to the current date in context. It only works correctly because you marked dim_date as a Date Table in Phase 2.
Finish · Final step
Organise into a measure table
By now you have 20+ measures scattered across different tables in the Fields panel. A dedicated measure table keeps them all in one place — clean, professional, and easy to find when building visuals in Phase 4.
1
Create an empty _Measures table
Enter Data
▼
▶ Home tab → Enter Data
  1. Go to Home tab → click Enter Data.
  2. A table editor appears. Delete any default columns. Name the table _Measures (the underscore pushes it to the top of the Fields panel alphabetically).
  3. Click Load. An empty table appears in your Fields panel.
2
Move all measures into _Measures
▼
  1. In the Fields panel, find a measure you created (e.g. Total Applications under fact_applications).
  2. Click it to select it. In the Measure tools tab at the top, find the Home Table dropdown.
  3. Change it from fact_applications to _Measures.
  4. Repeat for every measure. They'll all move into the _Measures table.
💡 You can also right-click a measure in the Fields panel → Edit → change the Home Table from there. Once all measures are in _Measures, your data tables (fact_applications, dim_jobs etc.) only show their columns — much cleaner.
