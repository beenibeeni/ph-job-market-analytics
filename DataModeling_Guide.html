Understand first · Concept 1
What is a star schema?
A star schema is a way of organizing your tables so that Power BI can answer questions quickly and correctly. It's called a "star" because of how it looks in a diagram — one central table in the middle, with supporting tables branching out around it like a star.
1
The real-world analogy
▼

Think of a supermarket receipt. The receipt itself lists every item you bought — quantity, price, date. But it doesn't repeat the full product description on every line, or your full address on every purchase. That extra detail lives elsewhere (a product catalog, a customer record) and is just linked to each line by a code.

A star schema works the same way. Your fact table is the receipt — one row per event (one row per application). Your dimension tables are the product catalog and customer record — the reference information that gives context to each event.

💡 The benefit: instead of storing "Data Analyst, Hybrid, Manila, Kislap Labs" on every single one of the 2,660 application rows, you store the job details once in dim_jobs and just reference it with a job_id. Less repetition = faster queries = better dashboard performance.

Understand first · Concept 2
Fact tables vs dimension tables
The most important design decision in a star schema is knowing which table is the fact table and which are dimensions. Get this right and everything else follows naturally.
1
The one-question test
▼

Ask: "Does this table record something that happened, or does it describe something that exists?"

TableSomething that happened?Something that exists?Type
raw_applications✓ — a person appliedfact
raw_job_postings✓ — a job existsdimension
skills✓ — a skill existsdimension
dates✓ — a date existsdimension
⚠️ A common mistake is making job postings your fact table. But a posting is not an event — it's a thing that exists. The event is someone applying to it. That's why applications is the fact table.
2
What columns belong in each type
▼
Fact tableDimension table
Foreign keys (job_id, date)Primary key (job_id, skill_name)
Measures — numbers you aggregate (interview_score)Descriptive attributes (job_title, company, work_setup)
Status/outcome columns (Hired, Rejected)Grouping columns (gender, education, age_band)
Grows with every eventStable — doesn't grow as fast
💡 A simple rule: if you'll ever put this column in a filter slicer or on an axis, it probably belongs in a dimension. If you'll ever sum or average it, it belongs in the fact table.
3
The 4-test framework — apply this to any table
▼

These four questions work as a cumulative vote. If most answers point to "fact", it's a fact table. Rarely do you get a split result.

TestQuestionYes →No →
1. The event testDid this row record something that happened?FactDimension
2. The timestamp testDoes it have a date or time column?Probably factProbably dim
3. The measure testWould you ever sum, count, or average rows from it?FactDimension
4. The growth testDoes it grow with every new event?FactDimension
⚠️ The tricky case — raw_job_postings. It has a date (posted_date), which makes it feel like a fact. But run the tests: it doesn't record a transaction, you filter by it rather than measure it, and it grows slowly. Three out of four point to dimension. The date column alone doesn't make something a fact table — the question is whether the date marks a transaction or just when something started existing. A job posting's date is the second kind.
💡 The same table can be a fact in one project and a dimension in another — it depends on what question your dashboard is answering. If you were building a dashboard purely about job posting activity with no applications data, job_postings could be your fact. But here, applications are the events and postings are the context. That makes applications the fact.

Why skills need two tables (many-to-many explained)
▼

One job posting has many skills ("SQL, Python, Power BI"). One skill appears in many job postings. This is called a many-to-many relationship — and Power BI struggles with it directly.

The solution is a bridge table: a simple two-column table that lists every job-skill combination as its own row.

3
Primary keys and foreign keys — how to identify them
▼

Keys are what make relationships work in Power BI. Understanding them tells you exactly which column to drag to which when setting up relationships in Model view.

Primary key — uniquely identifies every row in a table

No two rows can share the same value, and no row can be blank. Quick test: use Column Distribution in Power Query — if "distinct" and "unique" both equal the total row count, every value appears exactly once. That's your primary key.

Foreign key — references the primary key of another table

It doesn't have to be unique — it usually repeats a lot, because many rows in the child table point to the same parent row. Look for columns that share the same name and data type across two tables — that naming match almost always signals a foreign key.

TablePrimary keyWhy it's unique
dim_jobsjob_idJP0001, JP0002 — each posting has one ID, never repeats
dim_skillsskill_nameSQL, Python, Power BI — each skill listed once
dim_dateDateEach calendar date appears exactly once
fact_applicationsapplication_idAPP00001, APP00002 — each application has one ID
bridge_job_skillsjob_id + skill_nameNeither alone is unique — the combination is (composite key)

Foreign keys in your model

Table · columnPoints toMeaning
fact_applications · job_iddim_jobs · job_idWhich job was applied to
fact_applications · date_applieddim_date · DateWhen the application was submitted
bridge_job_skills · job_iddim_jobs · job_idWhich job this skill belongs to
bridge_job_skills · skill_namedim_skills · skill_nameWhich skill this row refers to
⚠️ Referential integrity: every foreign key value must exist in the primary key table. If fact_applications has a job_id of JP0099 but dim_jobs has no JP0099 row, that application becomes an orphan — it won't appear correctly in visuals. In your cleaned dataset this shouldn't be an issue, but in real-world data it's worth checking. In Power Query: merge the two tables on job_id with a Left Outer join, then filter for rows where dim_jobs columns are null — those are the orphans.
💡 The 1-to-many rule: the primary key always sits on the "one" side (dimension), and the foreign key sits on the "many" side (fact or bridge). One job in dim_jobs → many applications in fact_applications. Power BI uses this direction to filter correctly: a slicer on work_setup (dim) filters down into applications (fact), never the other way around.
Build the model · Step 1
Create dim_jobs
This is the easiest step — dim_jobs already exists as raw_job_postings. You just need to rename it and remove the skills_raw column (which will live in its own tables instead).
1
Rename raw_job_postings to dim_jobs
Power Query Editor
▼
▶ Home tab → Transform Data (to re-open Power Query)
  1. Open Power Query Editor: Home tab → Transform Data.
  2. In the Queries pane on the left, right-click raw_job_postings.
  3. Click Rename and type dim_jobs. Press Enter.
2
Remove the skills_raw and job_description columns
Transform tab
▼
  1. In the dim_jobs query, click the skills_raw column header.
  2. Hold Ctrl and also click job_description.
  3. Right-click either selected column → Remove Columns.
💡 We're removing these because skills will live in their own tables (dim_skills and bridge_job_skills). Keeping skills_raw in dim_jobs would create confusion — the skills info would exist in two places. job_description is also no longer needed once skills_raw has done its job.
Build the model · Step 2
Create dim_skills
dim_skills is a list of every unique skill name across all job postings. You'll create it as a new query by referencing dim_jobs, expanding the skills_raw column, and deduplicating. This is all done in Power Query.
1
Duplicate dim_jobs before removing any columns
▼

You need to create dim_skills and bridge_job_skills from dim_jobs before removing skills_raw — because once skills_raw is gone from dim_jobs, any query based on it won't have it either. The key is using Duplicate, not Reference.

⚠️ Reference vs Duplicate: A Reference is a live link — it always reflects dim_jobs as it currently stands, including any columns you've already removed. A Duplicate takes an independent snapshot at that moment. For this task you need Duplicate, so the copy captures skills_raw before it's removed.
  1. In Power Query, make sure you are on the dim_jobs query and have not yet removed skills_raw or job_description.
  2. Right-click dim_jobs in the Queries pane → click Duplicate. A new query appears called "dim_jobs (2)".
  3. Rename it to dim_skills.
  4. Right-click dim_jobs again → Duplicate → rename this one to bridge_job_skills.
  5. Now go back to dim_jobs and remove skills_raw and job_description (Step 3 above). The two duplicates are independent — removing columns from dim_jobs does not affect them.
💡 After this you should have three queries in the left panel: dim_jobs (clean, no skills columns), dim_skills (still has skills_raw), and bridge_job_skills (still has skills_raw). The next substeps will trim each duplicate down to only what it needs.
2
In dim_skills — keep only job_id and skills_raw
▼
  1. Click on the dim_skills query in the left panel.
  2. Click the job_id column header, then hold Ctrl and click skills_raw.
  3. Right-click → Remove Other Columns (not "Remove Columns" — "Remove Other Columns" keeps only what you selected).

Build the model · Step 4
Create dim_date
dim_date is a special table — it's not created from your CSV data, but generated using a DAX formula directly in Power BI. It gives you a complete calendar from Jan to Jun 2026 with columns like Year, Month, Quarter, and Week — which Power BI needs for time intelligence calculations.
1
Close & Apply first, then create dim_date from the main canvas
Home tab → Table tools → New table
▼
  1. Click Close & Apply in Power Query to return to the main Power BI canvas.
  2. In the Table tools tab (or Modeling tab), click New Table.
  3. A formula bar appears — paste this DAX formula:
dim_date = ADDCOLUMNS( CALENDAR(DATE(2026,1,1), DATE(2026,6,30)), "Year", YEAR([Date]), "Month", MONTH([Date]), "MonthName", FORMAT([Date], "MMMM"), "MonthShort", FORMAT([Date], "MMM"), "Quarter", "Q" & QUARTER([Date]), "WeekNum", WEEKNUM([Date]), "DayOfWeek", FORMAT([Date], "dddd"), "YearMonth", FORMAT([Date], "YYYY-MM") )
  1. Press Enter or click the checkmark. A new table called dim_date appears in your Fields panel.
💡 CALENDAR(start, end) generates one row per day between those dates. ADDCOLUMNS then adds extra columns to each row — year, month name, quarter, etc. — all calculated from that date. This is your first real DAX formula!
2
Mark it as a Date Table
Table tools → Mark as date table
▼
  1. Click anywhere on the dim_date table in the Fields panel to select it.
  2. Go to Table tools tab → click Mark as date table.
  3. In the dialog, set the date column to Date → click OK.
💡 This tells Power BI "use this table for all time intelligence calculations." Without it, functions like TOTALYTD, SAMEPERIODLASTYEAR, and DATESMTD won't work correctly.

Connect everything · Step 1
Open Model view
Model view is where you visually connect your tables with relationships — like drawing lines between them. It's accessed from the left sidebar in Power BI Desktop.
1
Navigate to Model view and arrange your tables
▼
  1. On the left side of Power BI Desktop, look for the vertical icon bar. Click the Model view icon — it looks like three connected boxes (below the Report and Data view icons).
  2. You'll see all your tables laid out as cards, possibly overlapping randomly. Drag them to arrange like the star schema diagram: fact_applications in the center, dim_jobs to the right, dim_date to the top, dim_skills to the bottom-right, bridge_job_skills between dim_jobs and dim_skills.
  3. Arranging them visually first makes it easier to draw relationships without lines crossing everywhere.
💡 Power BI may have already auto-detected some relationships (shown as lines between tables). Check if they're correct before adding new ones — incorrect auto-detected relationships can cause wrong results in your visuals.
Connect everything · Step 2
Set up relationships
A relationship tells Power BI "these two columns in different tables contain the same values — use them to connect the tables." You create one relationship per connection line in the star schema.
1
How to create a relationship
▼

Two ways — pick whichever feels easier:

Option A — drag and drop: In Model view, click and hold the column name inside one table card, then drag it onto the matching column in another table card. A line appears between them.

Option B — Manage Relationships dialog: Home tab → Manage Relationships → New → pick both tables and their matching columns from dropdowns.

💡 Option A is faster and more visual. Option B is safer when tables have many columns and you want to be precise about which column you're selecting.
2
The 4 relationships to create
▼
From table · columnTo table · columnCardinality
dim_jobs · job_idfact_applications · job_idOne-to-many (1:*)
dim_jobs · job_idbridge_job_skills · job_idOne-to-many (1:*)
dim_skills · skill_namebridge_job_skills · skill_nameOne-to-many (1:*)
dim_date · Datefact_applications · date_appliedOne-to-many (1:*)
⚠️ Cardinality: "One-to-many" means one job in dim_jobs can match many applications in fact_applications (one job, many applicants). Always set the "one" side on the dimension table and the "many" side on the fact table. Power BI usually detects this automatically when you drag — just confirm it in the relationship dialog.
3
Cross-filter direction — which way to set it
▼

When you create a relationship, Power BI also asks about "cross-filter direction." This controls which way filters flow across the relationship.

RelationshipDirectionWhy
dim_jobs → fact_applicationsSingleFilters flow from dim to fact only
dim_jobs → bridge_job_skillsSingleStandard dimension to bridge
dim_skills → bridge_job_skillsBothNeeded so skill filters reach fact_applications through the bridge
dim_date → fact_applicationsSingleDate filters flow into applications
💡 "Single" means filters only travel one way (dimension → fact). "Both" means filters travel in either direction. The dim_skills → bridge relationship needs "Both" so that when you filter by skill in a visual, it correctly counts only the applications for jobs requiring that skill.
